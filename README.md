# Posts & Comments

Backend на Go: посты, дерево комментариев и GraphQL Subscriptions. Хранилище выбирается при запуске: память или PostgreSQL. API и бизнес-логика одинаковы для обоих режимов.

## Запуск

Нужен Go 1.25+ либо Docker с Compose.

```sh
go run ./cmd/server
```

По умолчанию используется память. GraphQL Playground: <http://localhost:8080>, endpoint: `/query`, WebSocket: `ws://localhost:8080/query`. `/healthz` проверяет процесс, `/readyz` — доступность хранилища. После перезапуска данные в памяти исчезают.

Docker без базы:

```sh
docker build -t posts-comments-service .
docker run --rm -p 127.0.0.1:8080:8080 posts-comments-service
```

Docker с PostgreSQL:

```sh
cp .env.example .env
# Укажите в .env случайный POSTGRES_PASSWORD (буквы/цифры или hex).
docker compose up --build -d
docker compose logs -f app
```

Compose поднимает БД, ожидает её готовности и запускает приложение с миграциями. По умолчанию БД доступна локально на порту 5433, приложение — на 8080. Данные сохраняются в именованном volume. В PowerShell для копирования файла используйте `Copy-Item .env.example .env`.

Для запуска только PostgreSQL: `docker compose up -d postgres`. Затем:

```sh
export STORAGE=postgres
export DATABASE_URL='postgres://posts:YOUR_PASSWORD@localhost:5433/posts?sslmode=disable'
go run ./cmd/server
```

PowerShell:

```powershell
$env:STORAGE = 'postgres'
$env:DATABASE_URL = 'postgres://posts:YOUR_PASSWORD@localhost:5433/posts?sslmode=disable'
go run ./cmd/server
```

При использовании специальных символов пароль в URL нужно percent-encode. `.env` читается Compose; для `go run` задайте переменные окружения явно. Секреты в Git не сохраняются.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `STORAGE` | `memory` | `memory` или `postgres` |
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `DATABASE_URL` | — | Обязателен для PostgreSQL; поддерживает параметры pgxpool |
| `AUTO_MIGRATE` | `true` | Применение встроенных SQL-миграций при старте |

Миграции находятся в `internal/storage/postgres/migrations`, встроены в бинарник и выполняются транзакционно. Таблица версий и advisory lock защищают повторный и одновременный запуск. Для отдельного запуска задайте `STORAGE=postgres`, `DATABASE_URL` и выполните:

```sh
go run ./cmd/server -migrate-only
# После этого приложение можно запускать с AUTO_MIGRATE=false.
```

## GraphQL

Для мутаций нужен заголовок `X-User-ID`, например `alice`. В Playground задайте HTTP HEADERS: `{"X-User-ID":"alice"}`. Автор берётся из заголовка, а изменение разрешения на комментарии проверяется хранилищем атомарно.

Это демонстрационная идентификация, не полноценная аутентификация: клиент может подставить любой идентификатор. При публичном развёртывании заголовок должен устанавливаться доверенным шлюзом после аутентификации; входящий пользовательский заголовок следует удалять.

Создание поста:

```graphql
mutation {
  createPost(input: {title: "Первый пост", body: "Текст", commentsEnabled: true}) {
    id authorID title commentsEnabled
  }
}
```

Список постов:

```graphql
query {
  posts(first: 10) {
    edges { cursor node { id title authorID createdAt } }
    pageInfo { hasNextPage endCursor }
  }
}
```

Корневой комментарий и ответ (подставьте ID, возвращённые API):

```graphql
mutation {
  createComment(input: {postID: "1", body: "Комментарий"}) {
    id postID parentID body
  }
}
```

```graphql
mutation {
  createComment(input: {postID: "1", parentID: "1", body: "Ответ"}) {
    id parentID body
  }
}
```

Пост с корневыми комментариями и непосредственными ответами:

```graphql
query {
  post(id: "1") {
    id title body commentsEnabled
    comments(first: 10) {
      edges {
        cursor
        node {
          id body authorID
          replies(first: 5) {
            edges { cursor node { id parentID body } }
            pageInfo { hasNextPage endCursor }
          }
        }
      }
      pageInfo { hasNextPage endCursor }
    }
  }
}
```

Все комментарии поста, включая ответы любой глубины, читаются плоскими страницами. `parentID` позволяет клиенту собрать дерево итеративно. Для следующей страницы передайте её `endCursor` в `$after`:

```graphql
query Feed($postID: ID!, $after: String) {
  post(id: $postID) {
    commentFeed(first: 50, after: $after) {
      edges { cursor node { id parentID body authorID createdAt } }
      pageInfo { hasNextPage endCursor }
    }
  }
}
```

Отключение комментариев автором (существующие остаются доступны):

```graphql
mutation {
  setCommentsEnabled(postID: "1", enabled: false) { id commentsEnabled }
}
```

Подписка на новые комментарии выбранного поста, включая ответы:

```graphql
subscription {
  commentAdded(postID: "1") { id postID parentID body authorID createdAt }
}
```

Поддерживается WebSocket-протокол `graphql-transport-ws` (а также устаревший `graphql-ws` для Playground). Подписки через обычный HTTP отклоняются. Подписку откройте до создания комментария в другой вкладке. Событие публикуется после успешной записи. При отсутствии, неправильном формате ID, запрете, ошибке курсора или валидации API возвращает GraphQL `errors` с кодом в `extensions.code`. Внутренние ошибки БД логируются на сервере; клиент получает `INTERNAL_SERVER_ERROR` без SQL и деталей подключения.

## Архитектура и хранение

```text
cmd/server                   конфигурация, запуск, миграции, graceful shutdown
internal/api                 схема, resolvers, DataLoader, HTTP/WebSocket
internal/service             валидация и сценарии использования
internal/domain              модели и ошибки
internal/repository          интерфейс хранилища
internal/storage/memory      синхронизация и индексы в памяти
internal/storage/postgres    pgxpool, SQL и встроенные миграции
internal/pagination          курсоры
internal/pubsub              подписчики и доставка событий
```

Комментарий хранит `post_id` и nullable `parent_id` — adjacency list. Глубина хранения не ограничена. Родитель должен уже существовать и принадлежать тому же посту; изменение родителя не предусмотрено, поэтому через API нельзя образовать цикл. В PostgreSQL это дополнительно защищено составным внешним ключом `(post_id, parent_id) → (post_id, id)`. Индексы `(post_id, id)` и `(post_id, parent_id, id)` обслуживают ленту и непосредственных детей. Рекурсивного обхода дерева и загрузки всего поддерева на сервере нет.

Посты и комментарии сортируются по возрастающему `id`. Пагинация — keyset: `id > after`, выборка `first + 1`; `first` от 1 до 100, по умолчанию 20. Курсор содержит версию, границу и область (пост/родитель/режим ленты), закодированные в Base64URL. Курсор другой ветки или неканоническое Base64URL-представление (в том числе с переносами строк) отклоняются. Это не секрет и не средство авторизации. Страницы показывают актуальные данные, без фиксации снимка на время обхода.

В памяти используются maps и упорядоченные срезы ID; поиск начала страницы — бинарный, чтение страницы стоит `O(log n + first)`. `RWMutex` защищает карты и индексы; наружу возвращаются значения, а не изменяемые внутренние объекты.

В PostgreSQL создание комментария и изменение разрешения блокируют строку поста. Проверка разрешения и запись выполняются в одной транзакции, а ID выделяется после блокировки. Это также сохраняет порядок фиксации комментариев одного поста. Создание постов сериализует короткий участок выделения ID и записи advisory lock для корректной пагинации при конкуренции.

Вложенные `comments`, `commentFeed` и `replies` собираются DataLoader в пакеты до 100 ключей. PostgreSQL выполняет один запрос с `UNNEST` и индексируемыми `LATERAL`-выборками на пакет, вместо запроса на каждого родителя. Количество обращений растёт с числом уровней/пакетов, а не с числом комментариев. Кеш отключён, чтобы мутации и длительные подписки не читали устаревшие страницы и не накапливали их в памяти.

Текст комментария ограничен 2000 Unicode code points (не байтами); пустые строки, некорректный UTF-8 и NUL отклоняются. Для постов: заголовок до 200, текст до 100 000 символов. HTTP body и WebSocket-сообщение ограничены 1 MiB, глубина GraphQL-запроса — 20, сложность с учётом размеров страниц — 10 000. Лимит запроса не ограничивает глубину хранимого дерева: для неё предусмотрена плоская лента. Обычные операции имеют timeout 10 секунд. У подписок отдельно ограничены 10 секундами проверка поста и каждый пакет чтения комментариев; сама подписка остаётся открытой до отмены или отключения.

Небольшой WebSocket transport передаёт выполнение GraphQL в gqlgen и управляет отменой операций. На соединение допускается 32 активные операции; повторный активный ID закрывает соединение кодом 4409 и отменяет подписки. Инициализация ограничена 5 секундами, heartbeat — каждые 20 секунд, ожидание pong — до 60 секунд, запись — до 10 секунд. Остановка сервера отменяет операции и закрывает соединения.

## Проверки

```sh
go fmt ./...
go vet ./...
go test -count=1 ./...
go test -race -count=1 ./...
go build ./...
go test -cover ./...
```

Unit-тесты покрывают бизнес-правила, Unicode, ошибки ID/родителя/автора, выключение комментариев, курсоры, конкурентный доступ, цепочку из 10 000 уровней, отмену и переполнение подписок. API-тесты проверяют HTTP-запросы, пагинацию, batching (с подсчётом обращений), лимиты, скрытие внутренних ошибок и доставку/отключение WebSocket-подписок.

Для интеграционных тестов PostgreSQL задайте `TEST_DATABASE_URL` на отдельную тестовую БД. Тесты создают уникальные схемы, применяют миграции и удаляют только свои схемы; роли нужны права `CREATE` в этой БД. Без переменной эти тесты пропускаются:

```sh
TEST_DATABASE_URL='postgres://posts:YOUR_PASSWORD@localhost:5433/posts?sslmode=disable' go test -race -count=1 ./...
```

В PowerShell задайте `$env:TEST_DATABASE_URL = '...'` перед командой. Интеграционные тесты проверяют миграции, ограничения БД, batching, конкурентную запись, цепочку из 1000 уровней и количество SQL-запросов сквозного GraphQL-запроса (пост и 360 комментариев). Ожидается около 5 запросов; тест допускает до 10 из-за планирования пакетов, но отклоняет запрос на каждого родителя.

При заданном `TEST_DATABASE_URL` подробный запуск этих двух проверок выводит фактически измеренное число SQL:

```sh
go test -v -count=1 ./internal/storage/postgres -run '^TestPostgres(GraphQLNestedQueryCount|DeepChainPagedWithoutTraversal)$'
```

CI запускает race detector с PostgreSQL, проверяет форматирование и генерацию, собирает Docker-образ и выполняет API-сценарий в контейнерах с обоими хранилищами. Тот же сценарий можно запустить против отдельного тестового экземпляра:

```sh
TEST_SERVER_URL=http://localhost:8080 go test -race -v -count=1 ./internal/api -run '^TestRunningServerWorkflow$'
```

Он создаёт тестовые посты и комментарии, проверяет вложенность, страницы, запрет комментирования и доставку события через WebSocket. Не направляйте его на экземпляр с рабочими данными. Без `TEST_SERVER_URL` этот тест пропускается.

После изменения GraphQL-схемы:

```sh
go tool gqlgen generate
```

Генератор закреплён в `go.mod`, сгенерированный код сохранён в репозитории.

## Компромиссы

Подписки работают внутри одного процесса; события не хранятся и не переигрываются, порядок уведомлений при конкурентных записях не гарантируется. Буфер подписчика — 64 события. Переполнение закрывает подписку, не блокируя запись; клиенту нужно переподключиться и перечитать данные. После переподключения возможна дедупликация по ID. Для нескольких экземпляров понадобятся общий брокер и transactional outbox; PostgreSQL-хранилище само по себе не распространяет события между процессами.

Записи комментариев одного поста сериализуются для атомарного запрета и устойчивого порядка пагинации; разные посты обслуживаются независимо. Хранилище в памяти предназначено для одного процесса и держит весь набор данных. Редактирование/удаление, полноценная аутентификация и долговечная доставка событий выходят за рамки задания.
